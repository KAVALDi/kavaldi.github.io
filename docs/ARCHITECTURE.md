# Архитектура

## Два контура

```
ПРИВАТНЫЙ КОНТУР (вне этого репозитория)             ПУБЛИЧНЫЙ КОНТУР (этот репозиторий)

  заметка / чат / файл
        │  импорт
        ▼
  очередь разбора ──► запись (Markdown + YAML)        content/   публичный снимок (JSON)
        ▲  одобрение         │                           │
        │                    │ visibility: public        │ build
   студия (127.0.0.1)        ▼                           ▼
        │              экспорт по белому списку ──►   dist/      статический сайт
        └── выпуск ──► проверка приватности ──────►  GitHub Pages (Actions)
```

Граница между контурами: одна функция: `buildPublicSnapshot` в `src/core/exporter.mjs`. Она берёт записи с `visibility: public` из проектов с `visibility: public` и переносит только перечисленные в ней поля. Сборщик сайта читает исключительно `content/` и о хранилище не знает, поэтому работает в GitHub Actions без доступа к приватным данным.

## Компоненты

| Путь | Назначение |
| --- | --- |
| `src/core/schema.mjs` | Типы записей, измерения состояния, виды связей и происхождения. Единственный список допустимых значений |
| `src/core/store.mjs` | Чтение и запись хранилища: файлы, история ревизий, журнал событий, Git-коммиты |
| `src/core/text.mjs` | Хеш, токены, TF-IDF, шинглы, построчный diff, трёхстороннее слияние |
| `src/core/importer.mjs` | Анализ материала, предложение действия, черновик, одобрение, смена видимости |
| `src/core/exporter.mjs` | Публичный снимок, очистка текста, расчёт устаревания |
| `src/core/privacy.mjs` | Поиск приватных фрагментов и секретов в публичных файлах |
| `src/core/release.mjs` | Выпуск: экспорт → сборка → проверка во временном каталоге, затем перенос |
| `src/core/github.mjs` | Календарь активности и сверка PR/Issue/коммитов |
| `src/core/ai.mjs` | Контракт AI-слоя (провайдеров пока нет) |
| `src/site/` | Генератор сайта и его дизайн-система |
| `src/studio/` | Локальный сервер и интерфейс редактора |
| `src/cli.mjs` | Командная строка `hub` |

Зависимостей две: `markdown-it` (рендер Markdown) и `yaml` (frontmatter). Остальное: стандартная библиотека Node.js.

## Принятые решения

### ADR-1. Источник истины: файлы Markdown в приватной папке

Знания хранятся как обычные `.md` с YAML-frontmatter. Их читает любой редактор, папка открывается как vault в Obsidian, история ведётся Git и снимками ревизий.

Отклонено: база данных (SQLite): хуже переносимость и ручная правка. Хранение в GitHub Issues/Wiki: данные оказываются у сервиса, а приватную часть там держать нельзя.

### ADR-2. Публичный репозиторий содержит только экспортированный снимок

Приватное хранилище лежит в другой папке (и в другом, приватном Git). В публичный репозиторий попадает `content/`: результат экспорта по белому списку. "Скрыть из меню" как способ непубликации не используется нигде.

Следствие: публикация это обычный Git-diff каталога `content/`, который можно прочитать до отправки.

### ADR-3. Состояние записи: четыре независимых измерения

`design`, `implementation`, `verification`, `docs`. Прежний проект показал, что "согласовано", "в PR", "в основной ветке", "готово для Wiki" и "опубликовано" расходятся (PR #190). Одного поля `status` нет и добавлять его нельзя.

### ADR-4. Дорожная карта, каталог и Wiki: представления одних записей

Карточка дорожной карты это запись с полем `roadmap.lane`. Отдельного файла дорожной карты нет, поэтому состояние в карте и на странице механики не может разойтись.

GitHub Projects, Discussions и GitHub Wiki не используются: это были бы вторые места ручного ведения тех же статусов. GitHub остаётся источником фактов о коде: состояния PR и Issue подтягиваются командой `hub sync` и хранятся рядом со ссылкой, а не переписывают состояния записи.

### ADR-5. Ядро работает без AI

Сопоставление выполняется правилами: точный повтор: по SHA-256 нормализованного текста, новая версия: по доле общих словесных 3-шинглов, близкие записи: по TF-IDF. Интерфейс прямо сообщает, что AI не использовался. Контракт для будущего провайдера описан в `src/core/ai.mjs`.

### ADR-6. Обновление записи: трёхстороннее слияние, приоритет у правок владельца

Когда приходит новая версия уже импортированного материала, система сливает три текста: черновик из прежней версии источника (основа), текущую запись и черновик из новой версии. Там, где владелец менял текст, а источник тоже изменился, остаётся вариант владельца, а расхождение показывается как конфликт.

### ADR-7. Собственный генератор сайта

Модель данных нестандартная (связи, четыре состояния, устаревание, постоянные адреса по id), а страниц мало. Свой генератор на шаблонных строках: около 250 строк, без сборщика и без клиентского фреймворка. Готовые генераторы (Astro, Eleventy, Docusaurus) потребовали бы адаптеров того же объёма и добавили бы зависимости.

Отклонено: SPA. Сайт должен читаться без JavaScript, JS нужен только поиску.

### ADR-8. Студия: локальный веб-сервер, а не плагин Obsidian

Импорт, сравнение версий и выпуск требуют интерфейса, которого в Obsidian нет, а плагин привязал бы ядро к одному редактору. Obsidian остаётся удобным редактором тех же файлов. Сервер слушает только `127.0.0.1`, проверяет заголовок `Host` и требует служебный заголовок у изменяющих запросов.

### ADR-9. Веб-Wiki и режим "как в игре": разные продукты

Сайт имеет собственную дизайн-систему (`src/site/assets/site.css`) и не воспроизводит окно игрового руководства. Режим "как в игре": отдельное представление по ссылке `ingame_url`. Сейчас она ведёт на прежний сайт, где такое руководство уже есть.

## Безопасность

- Импортируемый текст: данные. Markdown рендерится с `html: false`, в студии текст вставляется через `textContent`.
- Секреты в файлы не пишутся: токен GitHub берётся из окружения или у `gh`.
- Экспорт останавливается, если в хранилище есть ошибки структуры.
- Выпуск сначала собирается во временном каталоге. При найденной утечке `content/` и `dist/` не меняются.
- Правка файла вне студии обнаруживается по отпечатку содержимого, запись не перезаписывается молча.

## Как добавить проект

Создать файл `projects/<id>.md` в хранилище (см. [DATA_MODEL.md](DATA_MODEL.md)). Код менять не нужно: навигация, страницы и классификация импорта строятся из списка проектов.
